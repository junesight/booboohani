# 부부한의원 홈페이지 백업 및 롤백 가이드

이 문서는 부부한의원 홈페이지의 소스 코드와 배포 상태를 안전하게 보호하고, 장애 발생 시 원상태로 신속하게 복구하기 위한 절차와 규칙을 정의합니다.

---

## 1. 백업의 기준
부부한의원 홈페이지는 빌드 과정이 없는 순수 정적 웹사이트이며, 백업과 버전 관리는 다음 기준에 따릅니다.

1. **GitHub main 브랜치**: 소스 코드의 단일 진실 공급원(Single Source of Truth)입니다. 로컬 PC의 파일이나 채팅 기록보다 항상 `main` 브랜치를 기준으로 백업 및 복구를 수행합니다.
2. **Commit**: Git의 개별 변경 단위이자 복구 단위입니다. 모든 코드 변경은 의미 있는 단위로 커밋되어 고유의 해시값(SHA-1)을 갖습니다.
3. **Pull Request**: 개발/수정 작업의 논리적 묶음입니다. 코드 리뷰 결과와 검증 이력이 아카이브되어 변경 맥락을 역추적할 수 있습니다.
4. **GitHub Pages 운영 배포**: `main` 브랜치에 최종 반영되어 실제 운영 서버(`https://booboo.co.kr`)에 서빙 중인 실시간 캐시/CDN 상태를 말합니다.

---

## 2. 변경 전 확인 절차
새로운 변경 사항을 적용하거나 배포하기 전에 작업 환경의 안정성을 위해 다음 절차를 순서대로 수행합니다.

1. **최신 main 동기화**: 로컬 저장소로 이동하여 원격 `origin/main`의 최신 내용을 가져옵니다.
   ```bash
   git fetch origin
   git checkout main
   git pull origin main
   ```
2. **Working Tree 확인**: 현재 커밋되지 않은 변경 사항이나 임시 파일이 없는지 확인합니다.
   ```bash
   git status
   ```
   *상태가 `nothing to commit, working tree clean`인 경우에만 작업을 시작합니다.*
3. **최근 Commit 확인**: 최근 5개의 커밋 내역을 확인하여 원격 저장소와 정합성이 맞는지 대조합니다.
   ```bash
   git log -5 --oneline
   ```

---

## 3. 안전한 작업 브랜치 생성 방법
작업은 `main` 브랜치에서 직접 수행하지 않고, 다음과 같이 작업 목적별 명명 규칙에 맞춰 브랜치를 만들어 진행합니다.

1. **브랜치 생성 명령어**:
   ```bash
   git switch -c <작업_브랜치명>
   ```
2. **브랜치 명명 규칙**:
   - 기능 개발: `feat/seo-번호-설명`
   - 버그 수정: `fix/seo-번호-설명`
   - 문서 작업: `docs/seo-번호-설명`
   - 단순 유지보수: `chore/설명`

---

## 4. 배포 전 백업 태그
배포 전에 현재 배포 상태(커밋)를 태그로 고정해두어, 문제 발생 시 즉각 안전한 직전 커밋으로 롤백하거나 배포 상태를 역추적하기 위한 정적 북마크 개념입니다.

1. **명명 규칙**: `production-YYYY-MM-DD` 형식으로 지정합니다.
   - 예: `production-2026-08-03`
2. **생성 및 푸시 방법 (참고용)**:
   ```bash
   # 배포 시점의 커밋에 태그 생성
   git tag production-2026-08-03
   # 원격 저장소에 태그 푸시
   git push origin production-2026-08-03
   ```
   > [!IMPORTANT]
   > 이번 OPS-003 작업에서는 **실제 Git 태그를 생성하지 않습니다.** 가이드에 명시된 규칙만 숙지하십시오.

## 5. 과거 버전 확인 방법

### 특정 파일의 과거 내용 확인 (CLI)
특정 커밋 시점의 파일 내용을 터미널에서 확인하고자 할 때는 아래 명령을 실행합니다.
```bash
git show <commit_hash>:<file_path>
# 예: index.html의 특정 커밋(c11e55d) 버전 확인
git show c11e55d:index.html
```

### GitHub 웹 화면을 통한 확인
1. GitHub 저장소의 **Commits** 탭에서 확인하고자 하는 시점의 커밋을 선택합니다.
2. 특정 파일 페이지로 들어가 우측 상단의 **History** 버튼을 누르면 해당 파일의 역대 변경 이력을 볼 수 있습니다.
3. **Blame** 탭을 활성화하면 특정 코드 라인을 최종 작성한 작업자와 커밋을 한눈에 확인할 수 있습니다.

## 6. Git Revert를 이용한 되돌리기 (권장)
`git revert`는 히스토리를 삭제하지 않고, 되돌리려는 커밋의 변경 사항을 상쇄하는 **새로운 커밋**을 만들어 안전하게 복구하는 방식입니다.

### 단일 커밋 되돌리기
```bash
git revert <commit_hash>
```
명령어를 실행하면 자동으로 revert 커밋 메시지 작성을 위한 편집기가 열리며, 저장 후 커밋을 푸시하면 배포 환경에 즉시 반영됩니다.

### Pull Request 병합(Merge) 커밋 되돌리기
병합 커밋은 부모 커밋이 2개(본 브랜치와 병합 대상 브랜치)이므로, 되돌릴 때 어떤 부모 브랜치를 기준으로 복원할지 `-m` 옵션으로 명시해야 합니다.
```bash
# -m 1은 첫 번째 부모(일반적으로 병합 기준이 된 main 브랜치) 상태로 복원함을 의미합니다.
git revert -m 1 <merge_commit_hash>
```

### 여러 커밋 되돌리기
여러 작업을 연속적으로 되돌려야 할 때는 **가장 최신 커밋부터 역순(LIFO: 후입선출)**으로 하나씩 revert를 실행해야 병합 충돌을 최소화할 수 있습니다.
- 예: `Commit A` -> `Commit B(최신)` 순으로 적용된 상태에서 둘 다 취소하려면, `Commit B`를 먼저 revert한 뒤 `Commit A`를 revert합니다.
- **위험성**: 순서를 지키지 않거나 한 번에 복잡한 범위를 되돌리려 할 경우, 대규모 머지 충돌이 발생해 사이트 오작동을 유발할 수 있습니다.

## 7. 복구 시 절대 금지 규칙 (`git reset` 및 `force push` 금지)
운영 복구 및 롤백 진행 시 `git reset --hard` 및 `git push --force` 명령어 사용을 **엄격히 금지**합니다.

- **이유**: 원격 저장소의 히스토리를 물리적으로 삭제하거나 덮어쓰기 때문에, 다른 협업 작업자나 AI 에이전트의 로컬 저장소와 정합성이 깨져 심각한 코드 유실을 야기할 수 있습니다.
- **예외**: 로컬 전용 개인 작업 브랜치에서 실수한 커밋을 정리할 때를 제외하고, 공동 브랜치(`main`) 및 운영 배포 브랜치 복구에는 오직 `git revert`만 사용합니다.

## 8. 특수 리소스 복구 시 주의사항

### CNAME 파일 복구
- **위험성**: `CNAME` 파일이 누락되거나 변경된 채 배포되면, 커스텀 도메인(`booboo.co.kr`) 매핑이 해제되어 환자들이 사이트에 접속할 수 없게 됩니다.
- **대책**: 롤백을 위해 revert를 적용한 후, 파일 목록에 `CNAME` 파일이 누락되지 않고 정상적으로 루트 경로에 존재하는지 반드시 확인합니다.

### assets 폴더 복구
- **위험성**: 이미지나 폰트가 유실되면 사이트 UI 레이아웃이 깨지고 의료기관으로서의 신뢰도가 손상됩니다.
- **대책**: 복구 후 메인 배너, 약도, 원내 인테리어 이미지 등 핵심 리소스가 모바일과 데스크톱 화면에서 모두 정상 노출되는지 수동으로 접속하여 검증합니다.

## 9. 배포 후 검증 및 완료 조건

### 배포 후 검증 절차
1. **시크릿 모드 접속**: 브라우저 캐시의 영향을 배제하기 위해 크롬 시크릿 창을 열어 `https://booboo.co.kr`에 직접 접속합니다.
2. **HTTPS 리디렉션 검증**: `http://booboo.co.kr`로 접속을 시도하여 `https` 프로토콜로 정상 리디렉션되는지 확인합니다.
3. **콘솔 오류 검사**: F12 개발자 도구를 열고 **Console** 탭을 확인하여 붉은색 에러 메시지(스크립트 오류, 리소스 404 로딩 오류 등)가 없는지 점검합니다.

### 복구 완료 조건
- `https://booboo.co.kr` 운영 도메인 접속이 원활함.
- 브라우저 개발자 도구 콘솔의 에러 발생 건수가 `0`임.
- 롤백을 반영한 `revert` 커밋이 원격 `main` 브랜치에 정상 병합 및 배포 완료됨.

## 10. 장애 발생 시 인수인계 양식
롤백 후 추가 조치가 필요하거나, 작업 중 장애 상황을 다른 AI 도구 또는 작업자에게 인수인계해야 할 경우 다음 양식을 작성하여 이슈(Issue)나 소통 채널에 남깁니다.

```markdown
### 🚨 장애 및 롤백 인수인계 사항
- **장애 발생 시각**: YYYY-MM-DD HH:MM
- **장애 현상**: (예: 메인 페이지 접속 시 흰 화면 노출 및 script.js 40줄 에러)
- **원인 커밋/PR**: (예: commit abc1234 / PR #22)
- **조치 내용**: (예: git revert abc1234 실행 및 main 병합 완료)
- **현재 상태**: (예: 롤백 완료하여 정상 접속 가능하나, 원본 변경 기능 보완 필요)
- **남은 작업 / 분석 필요 항목**: (예: script.js의 이벤트 리스너 null 참조 에러 원인 분석)
- **다음 조치자 가이드**: (예: feat/fix-event-listener 브랜치에서 다시 작업 시작 권장)
```
